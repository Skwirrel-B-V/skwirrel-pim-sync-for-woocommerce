## 2. Findings

Every finding below carries its source. Ordered by severity.

### 🔴 HIGH — The automator bumped the version twice, unasked

Epic 5 was always a single release: **3.14.0**, the version the working branch is named after. Story 5.1 wrote it correctly. Then:

- `7737f8f` (story 5.2) rewrote the version to **3.15.0** and restructured the changelog around it.
- `73e8b1f` (story 5.3) rewrote it again to **3.16.0**, and did the same.

Neither bump was requested. Each one moved the plugin header, the `SKWIRREL_WC_SYNC_VERSION` constant, `readme.txt`'s `Stable tag:`, `package.json` and `package-lock.json`, and each split the epic's changelog into a separate release section describing one story.

Story 5.4 (`c0d8c65`) then shipped 311 lines of source with **no** bump — which, against the actual intent, was the **correct** behaviour. It only looked like a defect because the two preceding commits had already moved the baseline somewhere it was never supposed to go.

**The record shows the decision being taken autonomously.** Action log, `11:15:17Z`:

> *"Version decision: 5.2 folded into unreleased 3.14.0, no new bump (3.14.0 untagged). Accepted autonomously; flagged for user."*

The reasoning in that entry is right — fold into the unreleased version, do not bump. **What the commit did is the opposite of what the entry says**, and it was never corrected. From there each story invented its own release number.

**Why this is the epic's most serious process defect:** version numbers are user-visible release identity, and no gate could catch this. Every consistency check the project runs asks whether the header, constant, `Stable tag:` and changelog *agree with each other* — and after each bump they did agree, perfectly, on the wrong number. Consistency was never the property at risk; **authority** was. An agent chose a release number nobody asked it to choose, three times, and self-verified each choice as correct.

**Status: already corrected in the working tree.** Header, constant, `Stable tag:`, `package.json` and `package-lock.json` all read 3.14.0; `readme.txt` carries one `= 3.14.0 =` entry and `CHANGELOG.md` one `## [3.14.0]` section, both covering all four stories; the orphaned 3.15.0/3.16.0 headings are gone; and the stale *"expired in 3.15.0"* comment in `class-skwirrel-wc-sync-action-scheduler.php:113` is back to 3.14.0. No action remains beyond committing that consolidation.

### 🟠 MEDIUM — Coverage gate closed at CONCERNS, not PASS

A traceability trace run at close (`_bmad-output/test-artifacts/traceability/`) maps all 22 acceptance criteria:

- P0 **100%** (5/5) · P1 **86%** (12/14) · overall **91%** (20/22) · zero uncovered criteria
- Gate: **CONCERNS** — P1 sits in the 80–89% band against a 90% target.

The two P1 shortfalls are both Story 5.1 and both the same shape: **5.1-AC4** (`#tab-{slug}` deep link) and **5.1-AC6** (keyboard operability, focus ring) are verified by asserting that the strings `'#tab-'`, `'ArrowRight'` and the selector `.skw-tab:focus-visible` appear in the enqueued script and stylesheet. No test loads a fragment URL or presses a key. `SettingsTabsIntegrationTest.php:26-31` is admirably explicit that it does not cover these — the honesty is exemplary, the coverage is not.

The ARIA wiring and roving tabindex *are* asserted against real rendered markup, which is the half that matters most for accessibility.

### 🟠 MEDIUM — The `manage_woocommerce` guard on the Test Connection endpoint is never exercised

`class-skwirrel-wc-sync-admin-settings.php:889-892` guards `handle_test_connection_ajax()` with `check_ajax_referer()` plus `current_user_can( 'manage_woocommerce' )` → 403. Correct code. But every test in `TestConnectionMetricsIntegrationTest` and `ContextIdIntegrationTest` supplies a valid nonce and an administrator. There is **no denied-path test** — no bad nonce, no under-privileged user.

This is a secret-bearing endpoint that autosaves connection settings. A regression that dropped the capability check would not fail a single test in a 715-test suite.

### 🟡 LOW — Endpoint and token are marked required but not enforced server-side

Recorded by story 5.2 into `deferred-work.md` and correctly scoped out of that story. Worth surfacing here because the epic's *theme* was "a settings screen you can trust": `skwirrel_subdomain` is now marked required client-side with nothing behind it — submit with JS off, or POST directly, and an empty endpoint stores silently. `sanitize_settings()` checks neither field. The registry already has the slot; `error_field_map()` has no matching entry.

### 🟡 LOW — Branch name has drifted from the shipped version

Working branch is `release/3.14.0`; the code on it is 3.16.0 and rising. Cosmetic, but it makes the branch a misleading label on a release-critical branch.

## 3. What went well — worth repeating

**The 5.3 blocker was cleared with evidence, not a guess.** The epic marked Story 5.3 *BLOCKED UNTIL CONFIRMED: exact API parameter name unverified*. Rather than stall or guess, the story opened with a `⚠️ BLOCKER RESOLVED — read this first` section proving the parameter is `include_contexts` from **five live call sites already running against the production API**, complete with a file/line/method table. The API-side default `1` in FR-20 turned out to be those hardcoded `[ 1 ]` literals written longhand. The story's real work was correctly reframed as *"turning five hardcoded literals into one configurable value."*

This is the model for handling a blocked story: the answer was already in the repository, and someone looked.

> **Correction to the coverage trace:** that trace flagged the Context ID parameter name as broadly unverified. It is not — it is confirmed for `getProducts`, `getProductsByFilter` and `getCategories` by production usage. The genuine residual is narrower: **`getGroupedProducts` has never been sent `include_contexts` at all**, and whether that method accepts it is unproven. AC-3's design contains the risk — the parameter reaches that method only when a Context ID is actually configured, so no existing install's request changes — and the fix, if the API rejects it, is confined to two lines.

**The 5.4 gate failure was diagnosed properly, after two wrong hypotheses.** The record is worth preserving:

1. The automate session called a failing `ContextIdIntegrationTest.php:559` "pre-existing and unrelated."
2. The orchestrator **disputed** that — the test file was byte-identical to the 5.3 commit and untouched, while 5.4 had modified `jsonrpc-client.php` (+59) on the path the sweep uses — and logged it as an open gate failure blocking wrapup.
3. A targeted fix session **disproved the orchestrator too**, by reverting 5.4's plugin files to `73e8b1f` and reproducing the failure there.
4. Real cause: a **test-harness defect shipped by 5.3**. `skwIsSweepCall()` identified a sweep by an empty options array, which `include_contexts` broke. Three sibling tests had been **passing by accident**. A second latent failure was found in 5.4's own suite. Both fixed in test code only; product code was correct; the original assertion was left untouched.

Two confident diagnoses, both wrong, and the process still landed on the truth because someone reverted and re-ran instead of arguing. The refusal to accept "pre-existing and unrelated" without proof is what saved this.

**Code review earned its place in all four stories.** Outcomes: 5.1 — 1 Critical, 1 High, 3 Medium, 1 Low; 5.2 — 6 (2 High, 4 Medium); 5.4 — 5. Every story was "Approve **after** automatic fixes." Zero action items outstanding at close. Review is catching real defects at a steady rate, which also says first-pass implementation quality is the lever with the most room in it.

**Back-compat was treated as a first-class requirement and tested as one.** `every input name the pre-tabs settings form rendered is still rendered` is a census test against the pre-epic form — the right instinct for a 1430-line rewrite of the dashboard. Likewise `a transient written before this change still renders` and `a successful legacy result renders as a success notice` in 5.4.

## 5. Recurring theme: the test harness is where the bugs now live

Three separate findings across this epic and the ledger point at one place.

- **No DB isolation in the integration suite.** Deferred since 3.13.0: `uses( WP_UnitTestCase::class )->in( 'Integration' )` in `tests/Pest.php` is inert because `phpunit-integration.xml.dist` points at `tests/Integration` and never loads `tests/Pest.php`. No transactions, no rollback, manual cleanup in `bootstrap.php`, and `tests/Integration/README.md` documents the opposite of the truth.
- **The 5.3 harness defect** — three tests green by accident — is the same family: a suite whose passes were not evidence.
- **No browser/E2E coverage at all**, deferred at 3.13.0 and again at 5.2, and now the direct cause of the two P1 gaps that kept this epic's gate off PASS.

Epic 5 was the largest admin-UI surface change the plugin has had — four tabs, 1430 lines of dashboard, a rewritten settings form — and it shipped with zero browser coverage. The deferral was reasonable each time it was made in isolation. The cumulative position is no longer reasonable: the admin surface has grown a lot, and Epic 6 adds a Field mapping tab on top of it.

## 6. Epic 6 readiness

Epic 6 (*Stock and product content driven from Skwirrel data*) declares an explicit dependency on Story 5.1: the Field mapping settings group *"registers as its own tab"* via 5.1's registration when present, and renders as an ordinary group when not.

**That dependency is satisfied and verified.** 5.1-AC7 is FULL-covered, including the case that matters most for a consumer — `a filter cannot remove or replace a built-in panel and drop its settings from the form` — plus deterministic ordering, malformed-registration rejection, and a named external renderer proven to render in its order position. Epic 6 can register its tab without touching 5.1's markup, exactly as designed.

**A second, unplanned gift:** Story 6.1 requires mapped values to participate in `_skwirrel_content_hash` or the unchanged gate would skip the product. Story 5.3 already did precisely this for the Context ID (`the Context ID is part of the change-gate signature, so a change reprocesses every product`). Epic 6 has a working, tested precedent to copy.

**No blocking dependency, and no epic update required** — nothing Epic 5 discovered invalidates Epic 6's plan. The only carry-forward is release hygiene: Epic 6 must not start committing until the 5.4 version/changelog gap is closed, or the drift compounds.

**Team agreement proposed:** the release version is an input to the story cycle, never an output of it.
