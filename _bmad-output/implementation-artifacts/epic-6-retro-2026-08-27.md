## 2. Findings

Ordered by severity. Every finding carries its source.

### 🔴 HIGH — The one story that skipped the review harness is the one that failed the gate

Stories 6.1–6.4 all record `orchestration-6-20260826-143018` and all carry a **Review Findings** section.
Story 6.5 records *"claude-opus-5 (in-session)"* and has **no Review Findings section at all**. No code review ran on it.

All three P1 coverage gaps in Epic 6 are 6.5's:

- **GAP-1 · 6.5-AC4 · uncovered · risk 6** — nothing tests that a re-sync refreshes stored `_skwirrel_document_attachments` names. This AC *is* the entire delivery mechanism of the fix: every existing shop stores raw filenames today.
- **GAP-2 · 6.5-AC1 (second clause) · partial · risk 4** — the wiring from resolver → `$doc['name']` → `get_documents_for_product()` → template is untouched by any test. Sharp edge the story documented itself: `get_documents_for_product()` **drops** any doc with an empty name, so a wiring defect does not render badly — the document silently disappears from the tab.
- **GAP-3 · 6.5-AC5 · partial · risk 3 · SEC** — `AttachmentHandlerDocumentNameTest` proves the resolver returns HTML verbatim (escaping is the consumer's job). No test asserts any of the three consumers still discharges it.

The resolver itself is pinned eleven ways. What is untested is precisely the path a customer experiences.

The comparison is the finding: the four reviewed stories produced **19 patch-level findings between them**, several of them real production defects (below). 6.5 producing zero is far more likely absence of review than absence of defects.

### 🟠 MEDIUM — The integration suite is not idempotent, and that is now load-bearing

`npm run test:integration` passes **215/215 from a clean database** and fails **43 tests across 9 files** against a database a previous run touched. The failures — missing SKUs, duplicate-SKU exceptions, `created: 0` — are indistinguishable in shape from real regressions.

A suite that goes red for reasons unrelated to the code trains its readers to disbelieve red runs. That is the mechanism by which a real regression gets waved through.

This now matters more than it did, because the working tree adds a **required CI integration job** (`.github/workflows/ci.yml`) closing the deferred items from Story 2.6 (2026-08-19) and Story 6.4. That job compensates with a `npx wp-env clean tests` step. The compensation is correct and honest — its own comment says *"keep this step until that isolation story lands"* — but it papers over the defect rather than fixing it.

### 🟠 MEDIUM — Epic 5's action item 4 was unachievable as written (correction to the record)

The Epic 5 retrospective diagnosed the missing DB isolation as a **load-path bug**: `phpunit-integration.xml.dist` points its testsuite at `tests/Integration` and therefore never loads `tests/Pest.php`, so the `uses( WP_UnitTestCase::class )->in( 'Integration' )` binding is inert. The prescribed fix was "fix the `Pest.php` load path."

**That diagnosis was wrong.** Evidence, from the new CI job's own comment:

> wp-env's WordPress test framework calls `PHPUnit\Util\Test::parseTestMethodAnnotations()`, removed in PHPUnit 10, so `WP_UnitTestCase` cannot be bound under Pest 3.

It is a framework incompatibility, not a configuration bug. Fixing the load path would not have produced transactions; it would have produced a fatal. The action item was un-actionable from the day it was written, which is part of why it went untouched.

The deferred-work entry from 3.13.0 (2026-08-19) carries the same wrong hypothesis and should be corrected alongside it, as should `tests/Integration/README.md`, which still claims isolation the suite does not have.

### 🟠 MEDIUM — 6.5's backfill correctness is conditional on release sequencing, and that condition lives only in a story file

Story 6.5 ships no migration for existing shops' raw document filenames. It does not need one, because `__version` folds into `compute_sync_signature()` (`class-skwirrel-wc-sync-service.php:2475`), which seeds `payload_signature()` (`product-upserter.php:188`) — so every stored `_skwirrel_content_hash` mismatches after a version change and the first sync rewrites `_skwirrel_document_attachments` wholesale, even in `enforce` mode.

The story states the condition explicitly:

> **Note this remains true only because 3.14.0 ships as a new release**; had this landed as a patch to an already-released 3.14.0, the backfill would need a forced full sync instead.

**3.14.0 is still untagged.** If any of this work later lands as a patch to an already-released 3.14.0, every existing shop keeps raw filenames permanently with no repair path. The condition is recorded in one story file and nowhere in the release process or the release skill's checks.

### 🟡 LOW — The delta-sync blind spot got a bigger blast radius this epic

Deferred from 6.1's review, correctly scoped out of the story: in the default `content_hash_mode = observe`, the timestamp gate runs **before** the content hash is consulted, so an upstream custom-class value changed without advancing `product_updated_on` is skipped.

Always true; materially more consequential now. Epic 6 made product-level custom classes drive **stock and all product copy**. 6.2's review partly closed it — default `observe` mode now processes a known payload-hash mismatch even when the timestamp did not advance — but products with **no stored hash** retain the timestamp fallback.

### 🟡 LOW — `epic-6` reads `in-progress` with 5/5 stories done

Bookkeeping only. Corrected as part of this retrospective.

## 3. What went well — worth repeating

**The NFR-9 suite was mutation-tested. Nothing else in this repository can say that.**
Story 6.4's 18 tests all passed on the first run — and the story treated that as *"a reason for suspicion, not confidence."* The exact NFR-9 violation was deliberately injected into `apply_stock_mapping()` (an unresolved value writing `set_manage_stock(true)` + `set_stock_quantity(0)`); the suite went to **9 failed / 9 passed**; the mutation was reverted and the file verified byte-identical with `git diff --quiet`.

Every "unchanged" assertion in that suite has a **positive control** proving the write path can write — AC-1's control deliberately writes a different quantity (7) than the seeded value (42), so the assertion cannot be satisfied by the seed. Absent, `not_applicable`, empty, whitespace-only, non-numeric, malformed-ref and trade-item-scoped payloads are each tested **separately** rather than collapsed into one dataset, on the explicit reasoning that collapsing them "proves less than it appears to."

This is the direct answer to Epic 5's closing theme — *"the test harness is where the bugs now live."* It is the standard the rest of the repository should be read against.

**Epic 5's version lesson held, five for five.**
Every story record carries an explicit *"Version deliberately not bumped — stays on 3.14.0"* note with its reasoning. Epic 5's most serious process defect did not recur once. Noted with one caveat under follow-through below.

**Code review kept catching production defects, not test gaps.**
- **6.3:** a mapped long description containing only disallowed markup is non-empty *before* `wp_kses_post()` and `''` after — the ordinary upsert paths would then write that empty description. An NFR-9 violation inside the epic whose entire purpose is NFR-9, caught in review.
- **6.3:** whitespace-only mapped text was accepted as resolved, replacing a valid title.
- **6.2:** managed-stock state not cleared when a variation becomes price-on-request.
- **6.4:** review remediation found and fixed a genuine production defect *while writing tests for it* — the external-price `price_on_request` branch now preserves an existing variation price in both variation write paths.
- **6.1 / 6.3:** the custom-class whitelist could filter out the very class holding a configured mapped feature, leaving the mapping silently inert.

**Stories corrected their own stale premises instead of obeying them.**
- 6.1's spec said *"Story 5.1's tab registration does not exist yet — do not build a tab."* 5.1 had shipped. Dev resolved in favour of the code, rendered the ordinary field group the AC actually requires, and recorded the deviation.
- 6.2 deviated from Task 2/3's literal wording on price-on-request, because following it would have written an explicit `stock_status` alongside a managed quantity — which WooCommerce recomputes on save, undoing the rule. Price-on-request variations are excluded from the helper entirely instead.
- 6.3 caught the story's own main trap: `format_custom_feature_value()` handles `T` but not `B` (big text), and a long description is very likely a `B` feature. A naive delegation would have shipped a mapping that silently resolved to nothing.

**6.5 avoided a silent file-corruption trap.** Line 262's `$name` fed both the link text **and** `import_file()`, which derives the stored file's extension from it. A human title has no extension — every `.dwg`, `.xlsx` and `.zip` would have been stored as `.pdf`. Splitting `$import_name` (`file_name` only) from the display name prevented it, and fixed a latent instance of the same bug for attachments lacking `file_name`.

**Shared code was factored, not duplicated.** 6.3 lifted 6.1's ID-or-code matching into one `matching_features()` generator both resolvers share, re-ran 6.1's and 6.2's 21 existing tests against the refactor **before** adding anything new, and left value extraction separate by design (stock wants raw `numeric_value`, prose wants the formatted value). 6.1's stock mapping inherited 6.3's `normalize_feature_ref()` hardening for free.

## 5. Recurring theme: coverage concentrates where the harness runs, not where the risk is

Two epics now point at the same shape.

- Epic 5's gate stopped at CONCERNS on two P1 gaps, both in **Story 5.1**, both asserting UI behaviour by grepping source strings.
- Epic 6's gate stops at CONCERNS on three P1 gaps, **all in Story 6.5** — the one story that ran outside the orchestration and never got a code review.

In both epics the *core logic* was pinned to an unusually high standard (6.4's mutation testing being the high-water mark for the project), and the *delivery path* — what a user actually touches — was where coverage thinned. The difference in Epic 6 is that the cause is now identifiable and cheap to fix: it is not a missing test philosophy, it is a story that bypassed the process the other four followed.

The corollary is encouraging: the harness works. Four stories through it produced 19 patch findings, several of them real defects that would have shipped. The lever is making sure every story goes through it, not making the harness stricter.

### Team agreements

1. **Every story goes through the review harness — no exceptions for "small" or "one-line" stories.** Story 6.5 was described in its own epic entry as *"the defect is one line."* It shipped outside the orchestration, got no code review, and produced every coverage shortfall in the epic. The four reviewed stories produced 19 patch findings between them. Size does not predict risk; process coverage predicts findings.

2. **An action item without a story does not happen.** Epic 5's three untouched items were all "own story, later." Its three completed items all had commits. From now on, any retrospective action item above Low criticality either goes into `sprint-status.yaml` as a story or is explicitly recorded as accepted-and-closed. There is no third state.

3. **A retrospective action item must be verified achievable before it is written.** Item 4 of Epic 5 prescribed a fix that would have produced a fatal. An item nobody can complete is indistinguishable from an item nobody attempted.

4. **A new suite that passes on its first run is suspect until it has been made to fail.** Story 6.4's mutation test is the pattern; apply it to any suite whose purpose is detecting a regression.
