## From GH-40 status handling (spec-gh-40-product-status-handling, 2026-07-22)

- **Story 2 — Deprecated lifecycle (immediate next story).** Built ON Story 1's mapping. Adds a custom `deprecated` WooCommerce post status as a fourth mapping target, a per-product counter meta `_skwirrel_deprecated_sync_count`, and a setting `deprecated_remove_after_syncs` (0 = immediate, else N). Anything mapped to `deprecated` is set to that status; the counter advances once per sync-pass that processes it while deprecated (present products advance on any sync; `__missing__` products advance only in the full-sync purge); when the counter exceeds the threshold the product is moved to **trash** (never permanently deleted). Counter resets when the product returns to a visible status. New class `class-skwirrel-wc-sync-deprecated-status.php` (register status, admin filter/label), wired in bootstrap + `Skwirrel_WC_Sync_Plugin`; escalation applied in the upserter (present) and purge-handler (`__missing__`); settings + dashboard add the Deprecated option and threshold input. **Verify** a `deprecated` product is non-purchasable/hidden like draft and appears under its own admin status filter, incl. REST/exports. *Deferred:* purely to de-risk — Story 1 ships the mapping value first; user chose the lightweight split on 2026-07-22.

- **Trash-aware upsert lookup (duplicate products on re-appearance).** Surfaced by the GH-40 Story 1 review. `find_by_external_id()` / `find_by_skwirrel_product_id()` exclude `post_status IN ('trash','auto-draft')`, so a Skwirrel product moved to trash (now possible for ANY admin-mapped status, not just `product_trashed_on`) that later re-appears active is not found and is **re-created as a duplicate carrying the same `_skwirrel_external_id`**. Pre-existing latent bug, materially amplified by Story 1's status→trash mapping. Proper fix = make the upsert lookup trash-aware (find + un-trash/update in place instead of duplicating), which also improves the delete-protection "recreate on manual delete" path but has real blast radius (touches lookup + purge detection + delete-protection semantics). **DONE (2026-07-22): folded into PR #42 (Story 2).** Originally split out at planning, then pulled back in: Codex (PR #42 round 5) noted Story 2's automatic deprecated→trash escalation makes the duplicate fire automatically, so the lookup fix is really a prerequisite for shipping Story 2 safely — the maintainer decided to land it with Story 2 rather than after. Implemented: `find_by_external_id()` / `find_by_skwirrel_product_id()` now include trashed posts (exclude only `auto-draft`), so a trashed Skwirrel product is revived/updated in place instead of duplicated; a `guard_revive_from_trash()` helper keeps a trashed product trashed unless the incoming status is visible (publish/draft), preventing a trash↔deprecated cycle. The related-products batch resolver and the stale-purge SQL deliberately still exclude trash.

- **Permanent deletion after the trash step.** GH-40's original DoD listed a `draft → trash after X syncs → delete after Y syncs` ladder. The shipped design ends at **trash** (a "Deprecated → trash after X syncs" lifecycle); permanent `wp_delete_post()` is intentionally excluded per the project rule "never permanently delete." *Deferred:* revisit only if a client explicitly needs auto-purge of long-trashed products; would need a second threshold (Y) + a safe, reversible confirmation path. User confirmed remove=trash on 2026-07-22.

## From the top-level admin menu work (3.13.0, 2026-08-19)

- **The integration suite has no DB isolation — `tests/Pest.php` never binds `WP_UnitTestCase`.** Surfaced while writing `tests/Integration/AdminMenuIntegrationTest.php`: `get_parent_class()` on an integration test returns `PHPUnit\Framework\TestCase`, not `WP_UnitTestCase`, so the `uses( WP_UnitTestCase::class )->in( 'Integration' )` binding in `tests/Pest.php` is inert. There are therefore **no per-test DB transactions and no rollback** anywhere in `tests/Integration/`, which is why `tests/Integration/bootstrap.php` carries the manual `skwPurgeSkwirrelPosts()` cleanups. `tests/Integration/README.md` states the opposite and is wrong. Likely root cause (to confirm before fixing): Pest resolves `Pest.php` relative to the configured test root, and `phpunit-integration.xml.dist` points its testsuite at `tests/Integration`, so `tests/Pest.php` is never loaded in an integration run — the `class_exists()` guard is a red herring. *Deferred:* not a blocker (the suite is green and the manual cleanups compensate), but the fix has real blast radius — once the binding takes effect all nine integration files suddenly gain transactions plus `setUp`/`tearDown`, which will expose whatever latent assumptions the manual-cleanup approach has been hiding. Own story, straight after 3.13.0: fix the binding, re-verify all nine files, correct the README claim.

- **No browser/E2E coverage of the admin UI at all.** The 3.13.0 menu move is covered by `AdminMenuIntegrationTest.php` at the registration and filter level, but four things stay unverifiable without a browser and were checked by hand: that the menu actually *renders*, that the `dashicons-database-import` icon appears, that core puts `.current` on the right submenu row (`_wp_menu_output()` against a real admin request), and that `#skwirrel-sync-now` scrolls to the Sync Now block. There is no Playwright/Cypress setup in the repo (no config, no deps, no `tests/e2e/`). *Deferred:* standing up a browser toolchain to assert four facts about a menu that rarely changes is the wrong trade for this release. The real case for E2E is the rest of the admin surface, which today has zero UI coverage — "Sync now" and its background run, the settings forms incl. token masking, the live log viewer, the danger zone confirmation dialogs. Own story; the menu assertions come along for free. `bmad-testarch-framework` scaffolds Playwright and wp-env already serves a real admin. Relates to the CI gap noted above — integration and E2E both need a wp-env job in `.github/workflows/ci.yml`.
