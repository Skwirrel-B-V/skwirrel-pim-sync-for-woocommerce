
## Top-level admin menu (Jos + Sally decisions, implemented 2026-08-19)

Moved the plugin screen from a WooCommerce submenu to its own top-level menu. Not committed, version not bumped.

Verified in real core (WP 7.0, `~/.wp-env/1d7174484a4db7f8c75be74edc500229/WordPress`) and WooCommerce 10.8.0 source:
- Core top-level positions: separator2 = 59, Appearance = 60 (`wp-admin/menu.php:205,209`). `$menu` is sorted by `uksort($menu,'strnatcasecmp')` (`wp-admin/includes/menu.php:280`), so string float keys order naturally.
- WooCommerce positions: WooCommerce 55.5, Sales reports 55.6 (`includes/admin/class-wc-admin-menus.php:95,113`), Payments 56 (`src/Internal/Admin/Settings/PaymentsController.php:80`), Marketing 58 (`src/Internal/Admin/Marketing.php:80`). **58.9 is correct** — after the WC cluster, before separator2.
- WC's `menu_order` filter (`class-wc-admin-menus.php:301`) only moves separator-woocommerce + woocommerce + products; everything else keeps its relative order. Our item is not moved.
- `add_menu_page` collision handling: if `$menu[(string)$position]` is taken, core adds an md5-derived `* 0.00001` offset (`wp-admin/includes/plugin.php`). Nothing else claims 58.9.
- `submenu_file` filter confirmed: `apply_filters('submenu_file', $submenu_file, $parent_file)` at `wp-admin/menu-header.php:53`; match is `$submenu_file === $sub_item[2]` at `:229`. Core sets `$submenu_file` only for import.php (`wp-admin/admin.php:345`), so on our page we are the sole source.
- Link-only submenu entries: with no callback, `get_plugin_page_hook()` returns null and `file_exists(WP_PLUGIN_DIR.'/admin.php')` is false, so core falls to the raw-href branch `wp-admin/menu-header.php:276`. Verified — this is the `.php`-in-slug behaviour.
- **Correction to an assumption:** `add_submenu_page` writes `$_parent_pages[$menu_slug]` and `$_registered_pages[$hookname]` *unconditionally*, even with an empty callback. Harmless here because the signpost's key is the whole URL string, and re-registering PAGE_SLUG under itself yields the same `toplevel_page_skwirrel-pim-sync` hookname. Top-level highlighting does not read `$_parent_pages` at all — `get_admin_page_parent()` resolves via `$menu`.
- `admin_menu` (wp-admin/admin.php:163) fires BEFORE `admin_init` (:180), so the upgrade-set signpost flag first takes effect on the *next* admin page load.

Gates: pest 396 passed. phpcs clean (after phpcbf). **phpstan crashes at the 128M default memory limit — pre-existing**, confirmed by stashing the plugin dir and re-running. Clean with `--memory-limit=1G`. Worth pinning `memoryLimitFile` or a `--memory-limit` in the gate script.

## Session: admin-menu integration test (3.13.0, branch release/3.13.0)

Wrote `tests/Integration/AdminMenuIntegrationTest.php` (14 tests, 115 assertions) covering the

Mutation-checked (wrong position, missing parent rename, bad highlight fallback all fail loudly).

### Facts learned about this repo's integration suite (verified, not assumed)
- **`tests/Pest.php`'s `uses(WP_UnitTestCase::class)->in('Integration')` does NOT apply.** Tests run
  as plain `PHPUnit\Framework\TestCase` (`get_parent_class()` proves it). So there are **no DB
  transactions and no rollback** — `tests/Integration/README.md` claims otherwise and is wrong.
  That is why `bootstrap.php` carries manual `skwPurgeSkwirrelPosts()` cleanup helpers.
- WooCommerce's `WC_Admin_Menus` hooks are **not reliably registered** in the test bootstrap
  (`is_admin()` is false there). Observed present in one run and absent in the next. Re-including
  `WC_ABSPATH . 'includes/admin/class-wc-admin-menus.php'` is WooCommerce's own idempotent entry
  point (file short-circuits to `return new WC_Admin_Menus()` when the class exists).
- **`wp-admin/menu.php` is one-shot per PHP process**: it declares `_add_themes_utility_last()`, and
  the `wp-admin/includes/menu.php` it hands off to declares `add_cssclass()`, `add_menu_classes()`
  and (conditionally) `sort_menu()`. Requiring it twice is a fatal. Pattern that works: snapshot
  core's menu from an `admin_menu` callback at `-PHP_INT_MAX` during the single load, then restore
  that snapshot and fire `admin_menu` yourself for each later scenario.
- Requiring `wp-admin/menu.php` from inside a function silently builds the menu into function
  locals. Must `global $menu, $submenu, $admin_page_hooks, $_registered_pages, $_parent_pages,
  $_wp_real_parent_file, $_wp_submenu_nopriv, $_wp_menu_nopriv, $_wp_last_object_menu,
  $_wp_last_utility_menu, $compat, $menu_order, $default_menu_order;` first.
- **Raw `$menu` keys are not the rendered order.** WooCommerce returns true from
  `custom_menu_order` and rewrites the top level via `menu_order`, so core re-sorts with its own
  `sort_menu()` comparator in `wp-admin/includes/menu.php`. Any ordering claim has to go through
  that pass. Verified rendered order on WP 7.0 + WC 10.8:
  `… separator-woocommerce | woocommerce | products | payments | skwirrel-pim-sync | separator2 |
  themes.php …` — 58.9 lands exactly where intended.
- Tests are excluded from both `.phpcs.xml.dist` and `phpstan.neon.dist`, so test files do not
  affect those gates.
- Pre-existing (not mine): `SyncSafetyIntegrationTest` emits one deprecation —
  `Skwirrel_WC_Sync_Queue::truncate` deprecated since 3.8.0, called deliberately by that test.
