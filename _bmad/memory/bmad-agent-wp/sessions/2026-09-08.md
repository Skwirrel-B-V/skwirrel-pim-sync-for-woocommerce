# 2026-09-08

## Diagnosed: a client's sync queued but never ran

Screenshots showed three `skwirrel_wc_sync_step` Action Scheduler actions, all "Pending" for 3+
hours, plus Site Health flagging "A scheduled event has failed". Root cause: WP-Cron/loopback
not being delivered on that server — not a plugin bug. Confirmed the architecture along the way:
this build is a **resumable Action Scheduler state machine**, not the synchronous `run_sync()`
`.claude/rules/sync-service.md` describes — `begin_run()` logs "Sync started" and hands off to a
scheduled `skwirrel_wc_sync_step` action; everything else (`step_init`, fetch, etc.) runs in a
separate request. `sync-service.md` is stale on this point, worth a correction pass sometime.

## Built: stuck-sync warning + health check + Debug checklist (branch `feature/stuck-sync-warning`, off `release/3.14.0`)

- `Skwirrel_WC_Sync_Service::get_stuck_run_warning()` — new. Run state exists, heartbeat stale,
  `started_at` more than `STUCK_RUN_WARNING_THRESHOLD` (600s) ago → translated warning, names
  `DISABLE_WP_CRON` when set. Different failure than the existing `MAX_STALL` poison-loop guard:
  that recovers a run whose steps *are* executing but stalling; this catches a run whose first
  step never got picked up at all, so the heartbeat never goes fresh and nothing inside
  `run_async_step()` ever runs to detect it — only the UI, checking independently, can.
- Wired into the existing shared `#skwirrel-sync-banner` slot (`get_sync_banner_html()`) — already
  rendered on every tab (Dashboard/History/Settings/Debug) and already polled by
  `handle_sync_status()`. Had to also add a `stuck` flag to that AJAX response and teach the JS
  `render()` to treat `stuck` like `in_progress` — the poller only swapped banner HTML in when
  `in_progress` was true, so a stuck run (which is *never* in_progress) would have been invisible
  to the live poller even though the PHP-side logic was correct on first page load.
- Added an on-demand health check to the Debug tab, reusing **WP core's own**
  `WP_Site_Health::get_test_scheduled_events()` / `get_test_loopback_requests()` /
  `can_perform_loopback()` — verified real by reading `wp-admin/includes/class-wp-site-health.php`
  inside the running wp-env container (not guessed). `get_test_loopback_requests()` does one live
  `wp_remote_post()` to the site's own `wp-cron.php`, 10s timeout — on-demand click only, never on
  page load. Needs `require_once ABSPATH . 'wp-admin/includes/class-wp-site-health.php'` — not
  autoloaded outside the Site Health screen.
- Added a static "Sync not working? Check this first" checklist to the Debug tab per Jos's
