# Review a pull request

A wrapper around `code-review` (Matt Pocock's, copied into `.claude/skills/`,
see `MATTPOCOCK.md`). That skill finds the problems; this one decides where
they go. **All communication about the review lives on the PR**: the review,
its threads, and the replies in them. Nothing about the review goes only to
the chat; the chat gets one line with the PR link and the outcome.

Every comment starts with `> *This was generated by AI.*`, followed by a
proper answer in plain English: full sentences that someone reading the PR
next month understands without the code. Never post the disclaimer alone.
After posting, read the comments back and fix any that came out empty or cut
off (shell quoting breaks multi-line bodies; post them with `--input` and a
JSON file).

Two sides, like Codex and `codex-pr-babysitter`:
- **Reviewer** (steps 1-3): find the problems and post them.
- **Author** ("Handle the threads"): when the PR is ours, or the user hands
  over a review link and asks to check or respond to it.

## Review budget and completion

Keep one ledger per PR across callers, resumed sessions, and both review skills:
last reviewed head and review ID, settled finding IDs, Codex trigger/head,
round counts, terminal state and stop reason. Reuse existing session/task state
and GitHub review evidence; do not add heartbeat comments. A caller must not
reset the counters by invoking this skill again.

Allow at most **3 automatic reviewer rounds** per PR run unless the owner
explicitly chooses another limit. Count the initial review. At the cap, stop
and report unresolved findings; never mark the PR clean to satisfy the cap.
Keep the two independent review agents.

**Stop means stop monitoring.** On clean completion, merge, closure, owner
cancellation, or any stop condition, mark this run terminal. End its polling,
background checks, timers and PR activity subscription using the available
cancellation mechanism. Cancel only monitoring owned by this run, and report
any cleanup that cannot be confirmed. Ignore late events for a terminal run;
do not fetch, review or trigger Codex because of them. Restart only on an
explicit owner request. New commits after completion can require a review
before merging, but do not authorize restarting a completed babysitter.

## 1. Find the PR

From a number or URL, or the open PR of the current branch
(`gh pr view --json number,url,baseRefName,headRefOid`). No PR? Then this
skill does not apply: run `code-review` and report in the chat.

Read the PR state and head once. If merged or closed, stop immediately.
If this head already has a clean review and there is no new substantive
finding or reply to handle, reuse that result and stop before reactions,
worktree creation or agent calls. An explicitly requested fresh review may
override reuse. If only a substantive reply changed, verify that finding
without rerunning the code reviewers.

## 2. 👀 and review

1. **👀 on the PR description** when you start:
   `gh api repos/<owner>/<repo>/issues/<pr>/reactions -f content=eyes`.
   An earlier clean result no longer counts: remove your own 🚀 and 👍
   reactions from the description and minimize the 👌 comment
   (`minimizeComment(classifier: OUTDATED)`), so the PR never shows 🚀, 👍
   or 👌 next to a round in progress.
2. Run `code-review` in a checkout of the PR head. Never switch branches in
   a repo's main clone (`gh pr checkout` there can collide with work in
   progress). Use the PR's existing worktree if there is one (`git worktree
   list` in the repo, matching the PR's branch); otherwise make a temporary
   one, detached at the PR head:
   ```bash
   cd repositories/<repo>          # the repo's main clone
   git fetch origin <base> pull/<pr>/head
   git worktree add --detach ../<repo>-review-<pr> FETCH_HEAD
   ```
   A temporary review worktree is removed (`git worktree remove`) as soon as
   the round is posted. The repo must be cloned under `repositories/`; if it
   isn't, say so and stop. **Fixed point:** `origin/<base>` in the first round; in
   later rounds the `commit_id` of your last review, so only the new commits
   are reviewed.
3. **Later rounds also check every 🔴/🟠 finding from earlier rounds**,
   resolved or not: inline threads and findings in a review body. Resolving
   a thread is not settling it. Read the author's answer and check it
   against the code: 🔴 is settled only when it was fixed (the diff shows
   it) or rejected with evidence that holds; 🟠 also when deferred to an
   issue. A missing, empty, or disclaimer-only answer settles nothing.
   Repeat unsettled findings in the new review.
4. **No new commits since your last review?** Skip `code-review` (its diff
   would be empty) and only do step 3.
5. **UI change and the issue (or its parent) links a design?** Review the
   looks too, not only the code: build the CSS in the checkout, screenshot
   the changed screens at the design's width, and compare them with the
   rendered design in one image. A visible difference that the PR does not
   list as deliberate is a 🟠 finding (🔴 when the screen is plainly not the
   design). Post the comparison image or its path in the review body. No
   👌 on such a PR without that comparison.

## 3. Post it

**Findings -> one review, one thread per finding.** Submit a single review
with event `COMMENT`: the two-axis summary in the body, and an inline comment
per finding on the line it is about. Findings without a line, on a line
outside the PR diff, or on a deleted line, go in the body: GitHub rejects the
whole review if one inline comment is invalid. Inline comments are for added
or unchanged lines (`side: RIGHT`).

```bash
gh api repos/<owner>/<repo>/pulls/<pr>/reviews -X POST --input review.json
# review.json: {"commit_id": "<head sha>", "event": "COMMENT", "body": "...",
#   "comments": [{"path": "...", "line": 42, "side": "RIGHT", "body": "..."}]}
```

**Every finding starts with a priority badge**, like Codex's P1/P2:

| Badge | Meaning | Blocks 👌? |
|---|---|---|
| 🔴 **P1** | Bug, data loss, security, or the code does something the spec does not want ("looks wrong") | Yes, until fixed or rejected with evidence |
| 🟠 **P2** | Should fix in this PR: spec partly missing, missing test or docs, an unasked scope change that needs a decision, a hard standards violation | Yes, until fixed, rejected, or explicitly deferred |
| 🟢 **P3** | Nice to have: smells, soft standards, judgement calls | No, an answer is enough |

Format: the AI disclaimer on the first line, then
`🔴 **P1 · Spec (looks wrong):** <what, where, why it matters>`. The review
body ends with the count per badge (`🔴 1 · 🟠 3 · 🟢 8`).

**No findings, no open threads from you, and no unsettled 🔴/🟠 body
finding -> 👌.** Replace your 👀 reaction on the PR description with 🚀 and
👍, and post one PR comment: the AI disclaimer and
`👌 Reviewed, ready to merge.` (GitHub has no 👌 reaction, so the reactions
are 🚀 👍 and the 👌 is a comment.) Never give 🚀, 👍 or 👌 while one of your
threads is still open.

```bash
me=$(gh api user --jq .login)
gh api --paginate repos/<owner>/<repo>/issues/<pr>/reactions \
  --jq ".[] | select(.content==\"eyes\" and .user.login==\"$me\") | .id" |
  xargs -I{} gh api -X DELETE repos/<owner>/<repo>/issues/<pr>/reactions/{}
gh api repos/<owner>/<repo>/issues/<pr>/reactions -f content=rocket
gh api repos/<owner>/<repo>/issues/<pr>/reactions -f content=+1
```

Only touch your own reactions. Codex leaves its 👍 in the same place: the
reaction's author tells the two apart, and the 🚀 is only ours.

The author answers and resolves the threads, as with Codex. A new round
starts when they ask for one or push fixes.

## Handle the threads (author side)

Work the review the way `codex-pr-babysitter` works a Codex round (its steps
3-7), with our review's threads instead of Codex's:

1. **Read** every unresolved thread of the review, including human replies
   (GraphQL `reviewThreads`, first comment's author and body). Human replies
   are context; weigh them as the babysitter says.
2. **Verify before you judge.** Open the file at the line, trace the claim.
   Never decide from the comment text alone; outdated threads (`line: null`)
   are checked against the current head.
3. **Decide per thread**: FIX, FIX-LATER, REJECT, STYLE, or ASK (the
   babysitter's table). Defaults by badge: 🔴 is FIX unless verifying proves
   it wrong; 🟠 is FIX or an owner decision; 🟢 is FIX only when it is cheap
   and in the PR's own code, otherwise a short reply. Collect every ASK and
   scope question, and every FIX-LATER that needs a new issue, in one
   question to the owner (max four).
4. **Fix and push**: test-first where it changes behaviour (`tdd`), run the
   repo's checks, one commit per round (`fix: address review round N`).
   Red checks you cannot fix in one try: stop and report.
5. **Reply once in every thread** in plain English, with the AI disclaimer
   and a real answer: "Fixed in <sha>: <what changed>", "Not changing this,
   because <evidence>", or "Deferred to #N, because <reason>". Then resolve
   it (`resolveReviewThread`). Answer the findings from the review body in
   one PR comment, one line per finding with the same three outcomes; the
   next round checks the 🔴/🟠 ones against it.
6. **Minimize the review's main comment** as resolved
   (`minimizeComment(classifier: RESOLVED)`) so the PR shows a clean
   overview.
7. **Next round**: run the reviewer side on new commits only, within the
   shared round budget. Without new commits, settle replies against the
   existing code; do not launch the reviewers again. Stop when clean or at
   the cap, and apply the completion cleanup above.

Never merge, force-push, rebase, or close the PR from here.

## Merge rule

Our 👌 on the current head, plus a clean Codex result when Codex reviewed
the PR (Codex's own 👍, or a Codex review with no findings), is enough review to
merge; no other approval is needed. A push after our 👌 needs a new round
from us. Once Codex has been clean, don't trigger it again on your own, not
even after later fixes: a new Codex round is a human's call. Codex stopping
at its round cap is not clean: the owner decides. Merging itself still
needs the owner's yes.

**Related PRs use the same rule.** Require our review on their current head
and settle outstanding findings. Reuse an earlier clean Codex result after
later commits; do not automatically request another Codex review. If Codex
has never reviewed a related PR, obtain the owner's authorization before
starting it, as in `pick-up-issue`. A fresh Codex review after a clean result
always needs an explicit owner request. Relatedness does not start monitoring
or override a terminal run.

**When you merge** (on that yes): `gh pr merge <pr> --merge --delete-branch`
(retarget any PR stacked on this branch to its base first), then clean up
locally right away: remove the PR's worktree (`git worktree remove <path>`)
and its local branch (`git branch -d <branch>`; if it refuses because the
merge isn't in the local base yet, `-D` is safe once GitHub shows the PR
merged), and `git fetch --prune`. Run this from the repo's main clone, not
from inside the worktree. Uncommitted changes in the worktree: stop and ask
instead of removing it.
