# Pick up an issue

Take one issue from the Development board
(<https://github.com/orgs/Skwirrel-B-V/projects/2>) from "do we understand it?"
to "tested and ready to merge". The board is the source of truth: every step
below ends with the board showing where the issue really is.

Related: `grilling`, `tdd`, `review-pr` (wraps `code-review`, Matt
Pocock's, copied into `.claude/skills/`, see `MATTPOCOCK.md`), `pr`,
`codex-pr-babysitter`, `create-github-issue` (how issues are written). For
bug reports use `fix-bug-issue`: the same flow with triage and diagnosis up
front.

## Ground rules

- **Code changes happen inside the repo the issue belongs to**, never at the
  workspace root. Follow that repo's own `CLAUDE.md`/`AGENTS.md`. Run git only
  inside that repo.
- **`skwirrel-extra` is read-only.** If the issue belongs there, stop, say so,
  and leave the board untouched.
- **Never fabricate test data.** Test against real data or a real tenant. If
  that is not possible, say so and hand the item to the owner.
- **No Slack** unless the user asks.
- Every comment you post on an issue or PR starts with:
  `> *This was generated by AI.*`
- Write comments in plain language. Product people read them, not only
  developers.
- Set board fields with `gh project item-edit` (fields and option IDs come from
  `gh project field-list 2 --owner Skwirrel-B-V --format json`; never hardcode
  IDs). Fields used:
  - **Status**: Backlog, Ready, In progress, In review, In test, Blocked, Done
  - **Developer acceptance.**: Accepted, Needs clarification
  - **Size**: XS, S, M, L, XL
- Assign people on the issue itself, not the board item:
  `gh issue edit <number> --repo <owner>/<repo> --add-assignee <login>`
  (`gh project item-edit` cannot set assignees).
- **After every Status or Developer acceptance change on a sub-issue, and
  after closing or reopening one, update the parent** (see "Parent status").
- **Can't start or continue?** Tell the owner what is needed in one sentence
  or a few short bullets ("#123: waiting for an answer to my questions").
  No more than that.

## Reuse completed work

Keep a compact per-issue record of the current step, code head, environment,
decisions, review budgets and verification evidence. Resume at the first
unfinished step. Reuse issue context and project field IDs within the run;
refresh when comments, relationships, permissions or board configuration change.
Fetch the board item list once for a batch, not once per issue. Before setting
a field, compare its current value; skip unchanged writes and parent roll-ups.
After real changes, recompute affected parents from current child state.

Reuse passing checks only for the same code head, command/configuration,
environment and relevant data state. Evidence from CI or an earlier step may
satisfy a checklist item when it proves that exact scenario. After a change,
rerun affected checks; broaden to the required repo suite before hand-off.
Never reuse stale evidence or skip required checks. Record evidence once and
link it from the checklist rather than rerunning solely for another phase.

At a hand-off or blocked step, save the result and stop. Do not poll manual
tests, owner replies or merge status. Resume when explicitly requested;
review monitoring follows the review skills' own authorization and stop rules.

## Start gate

Never start an issue (Status **In progress**) unless both of these hold:

1. **Developer acceptance. = Accepted.**
2. **Size** is set (step 1 sets it when it accepts the issue).

The human who runs this skill on an issue is the "go"; no label is required.

If one fails, skip the issue: leave Status as it is, assign no one, and tell
the owner what is missing (ground rules). A resumed issue that is already In
progress or later has passed the gate; don't re-check it.

**Ready for an agent?** Before step 2, check that the issue has the
`ready-for-agent` label **or** an Agent Brief (an `## Agent Brief` section
in the body or a brief comment). Issues from `create-github-issue` have both.
If neither: warn the owner in one line ("#123 has no Agent Brief: without
one I am more likely to build the wrong thing") and offer to write the brief
first (`triage/AGENT-BRIEF.md`, posted as a comment). Start only after the
owner picks: brief first, or start without it.

**Needs clarification is a hard stop.** The issue waits until someone answers
in a comment. On a later run, read the comments after your question: answered
-> run step 1 again and set **Accepted** if it is now clear; not answered ->
skip it again.

## Parent status

A parent issue's Status follows its sub-issues. After every Status change on
a sub-issue, set the parent (and its parent, all the way up). A parent that
is not on the Development board yet is added first
(`gh project item-add 2 --owner Skwirrel-B-V --url <parent url>`); say so.

1. Ignore `[TEST]` sub-issues, closed-as-not-planned ones, and ones with
   Status **Skip**. A sub-issue closed as completed counts as Done. **Fail**
   counts as In progress (the work has to be done again). An open sub-issue
   that is not on the board, or has no Status, counts as Backlog (don't add
   siblings to the board for this).
2. Has any sub-issue reached **In progress** or later (including Blocked)?
   No -> leave the parent as it is.
3. Every sub-issue that is not **Blocked** is **In test** or **Done**, and at
   least one is **Blocked** -> parent = **Blocked**.
4. Otherwise the parent gets the **lowest** Status of its sub-issues, in this
   order: Backlog, Ready, In progress, In review, In test, Done. Anything below
   In progress counts as In progress, and so does Blocked. So: one sub-issue
   In progress -> parent In progress; all In review or later -> In review;
   all In test or later -> In test; all Done -> Done.

**Developer acceptance. rolls up too.** After every acceptance change on a
sub-issue, and after one is closed or reopened (a closed sub-issue no longer
counts), set the parent's (all the way up), from its open sub-issues
(`[TEST]` and **Skip** ones ignored, as in rule 1):

- Any sub-issue **Needs clarification** -> parent = **Needs clarification**.
- Otherwise, at least one **Accepted** -> parent = **Accepted**.
- Otherwise leave the parent as it is.

On the parent this is a signal, not a gate: the Start gate looks at the
sub-issue's own acceptance, so an Accepted sibling can still start.

Nothing else rolls up. Don't close, assign, or comment on the parent for
this: the question lives on the sub-issue that needs the answer.

## Which mode?

- Title starts with `[QA]` or `[TEST]` (or the issue is a checklist to verify
  existing behaviour) -> **QA mode**. Do step 0, then go straight to
  "QA mode" below: Q1 replaces steps 1 and 2. No worktree, no PR, no code
  review.
- Anything else -> **build mode**: steps 0-6 as written.

**Resuming?** Before any board change, check whether work on this issue already
exists: its Status on the board, a worktree or branch in the target repo
(`git worktree list`, `git branch -a`), or a PR (`gh pr list --repo <owner>/<repo> --state all --search <number>`,
in the issue's repo, not the workspace).
If so, continue at the step that Status and PR show. Never set Status back to
an earlier stage just because you are resuming. A PR that is already merged
(someone else merged it) still gets the cleanup from `review-pr` ("When you
merge") for its worktree and branch.

## 0. Who is the owner?

The owner is the person who started the skill. Look for a saved GitHub login in
memory (`github-login`). If there is none, ask once ("What is your GitHub
username?"), then save it to memory. Use it for every assignment and for
"for owner" below.

## 1. Read and accept

1. Read the issue fully: body, comments, linked issues, attachments, Definition
   of Done, size, iteration.
   - **Has it a parent?** (`gh api repos/<owner>/<repo>/issues/<n>/parent`;
     404 means none.) Read the parent too, body and comments, and its
     parent, all the way up. It says why this issue exists and what the
     sibling issues already cover.
2. Read the target repo's `CLAUDE.md`/`AGENTS.md` and look at the code the issue
   touches. Understanding the issue includes knowing where the change lands.
3. Decide: do I understand **what** to build, **why**, and **how we know it is
   done**?
   - Unsure? Run the `grilling` skill with the owner. Ask one question
     at a time and try to answer from the code first.
4. **Understood** -> set **Developer acceptance. = Accepted**. If **Size**
   is empty, estimate it from what you just learned and set it; mention the
   size you chose in the report. Then the **Start gate**. Passes -> step 2.
   Fails -> skip and say what is missing.
   - **Several issues?** Run steps 1.1-1.5 on all of them first, so every
     issue has its acceptance and size before any starts. Then start the
     first one that passes the Start gate.
5. **Not understood** (owner cannot answer either, or the owner is not around) ->
   post one comment saying exactly what you need to accept it (numbered
   questions, each answerable in a sentence, with your suggested answer where
   you have one), set **Developer acceptance. = Needs clarification**, and
   **stop**. Do not start work until it is Accepted (see Start gate).
6. **Too big?** Split it into sub-issues under the original, each sized and
   Accepted; then continue with the first one that passes the Start gate.

## 2. Ready and assign

Set **Status = Ready** and assign the owner, once the Start gate passes.

## 3. Build

1. Set **Status = In progress**.
2. Create a git worktree **of the target repo** as a sibling folder under
   `repositories/`, named `<repo>-<issue number>` (for example
   `repositories/skwirrel-core-699`), on a new branch named after the issue
   (for example `feature/699-short-slug`). Branch from the freshly fetched
   remote base (`git fetch origin` first, then branch from `origin/<base>`; see
   `repos.manifest` for the base, core is `develop`). Run git only inside that
   folder.
3. **Design first, when the issue (or its parent) links a design** (a Claude
   Design canvas, Figma, a mockup, screenshots). The design is the source of
   truth for how the change looks; the owner treats a mismatch as unfinished
   work, not as polish for later.
   - Before writing UI code, get the design's source and render it at the
     size it is drawn (a Claude Design canvas: `read` its `project/*.dc.html`
     files with the Artifact tool and render them in Playwright). Keep that
     screenshot.
   - Build the CSS before any visual check (core: `skw build`, or
     `make build` in `build/`). Without the compiled CSS the page renders
     unstyled and a browser check only proves behaviour, not looks.
   - After each UI slice: screenshot the same area of the real app at the
     same width, put it next to the design in one image, and look at it. Go
     on only when they match. Note every deliberate difference (and why).
4. Implement test-first with the `tdd` skill: agree the seams with the owner,
   then red -> green one slice at a time. Follow repo conventions and run the
   repo's own checks. Commit only when needed and never commit secrets or `.env` files.
5. Do not run destructive commands (`db:reset`, migrations on shared databases)
   without explicit confirmation.

## 4. Pull request

1. Push the branch and open a PR. **Write the body with the `pr` skill.**
   A UI change with a design puts the design-vs-built image in the PR's
   evidence (or links it), plus the list of deliberate differences. Link
   the issue (`Closes #N`, or `Refs #N` if the PR targets a feature branch).
   End the body with the attribution line from the session instructions.
2. Set **Status = In review**.

## 5. Review

Review with the `review-pr` skill (👀, threads, 👌, like Codex). Here you are
also the author, so you work its threads.

1. Run `review-pr` on the PR.
2. **Work the threads** as in `review-pr` "Handle the threads": verify,
   fix, reply once in every thread, resolve, minimize the review.
3. **Next round.** Follow `review-pr`'s shared budget (3 automatic rounds by
   default), duplicate protection and terminal cleanup. At the cap, report
   what remains and stop; do not restart it from this caller.
4. **Ask about Codex:** "Should `codex-pr-babysitter` run on this PR too? It
   needs a Codex account linked to the Codex GitHub app on this repo; without
   one, `@codex review` gets no answer." Ask only if no decision or clean
   result is recorded for this PR. Respect an earlier no; do not ask again
   after a test failure. Only on a yes, run it until Codex is
   clean or its round cap is hit.
5. **Review is done** when the `review-pr` merge rule is met. If Codex's
   fixes added commits after our 👌, review those commits within the same
   remaining budget. Stop if the budget is exhausted. Once Codex is clean, don't trigger it again: a new Codex round is
   a human's call. Then go on to step 6. Codex at its round cap without a
   clean result, or stopped for any other reason (usage limit, timeout, red
   tests, a scope question, a finding it could not settle): stop and tell
   the owner what is open.

## 6. Test

1. Set **Status = In test**.
2. **Write the criteria.** Build a checklist from the Definition of Done, the
   acceptance answers, and what the diff actually changed. One line per item:
   "do X, expect Y". Include edge cases and regression checks (what might have
   broken nearby). Post it as a checklist comment on the issue.
3. **Split the items:**
   - **Agent-checkable**: the repo's own tests, and running the real app (use
     the `run` skill, `skw` in core) against real data.
   - **For owner**: anything visual or a judgement call (layout, wording, "does
     this feel right"), and anything the repo cannot run headless. If a repo
     cannot be started here, say so and move those items to "for owner"
     instead of guessing.
4. **Run the agent-checkable items** and update the same comment. First map
   existing valid evidence to the checklist using "Reuse completed work".
   Run only checks not already proven. Run short checks directly; delegate a
   substantial batch only when it saves work. If delegating, use a supported
   lighter model when available, with the checklist, worktree path, PR link
   and binding rules (real data only, no code changes, no destructive commands,
   evidence per item). Do not launch both a primary and delegated copy of the
   same checks. Read delegated evidence before ticking anything; handle
   failures yourself. Tick passing items with short evidence (test output,
   screenshot, or query and result). Mark failing items with what you saw. Leave "for owner" items
   unticked and labelled **for owner**, and mention the owner in the comment:
   "@<owner>, these are your test steps."
5. **Failure loop.** If any item fails, set **Status = In progress**, fix it,
   push, and go back through step 5 (review) and step 6 (test) for the changes.
   Keep the existing review counters across this failure loop. If the review
   budget is exhausted, stop and report; do not reset it by returning to step 5.
6. **Ask to merge.** Only when the review is done (step 5.5) and every
   agent-checkable item passes, list what is left "for owner" and
   ask: "Can I merge this?" Do not merge without a yes.
7. After the merge: clean up the worktree and branch as in `review-pr`
   ("When you merge"), close the issue if it did not close itself (it does
   not when the PR targeted a feature branch), and leave **Status = In
   test** until the owner has done the "for owner" items.

## QA mode

For issues that verify behaviour instead of building it (for example
`[QA] v2 verify: ...`). The issue is the test plan: a checklist, a Definition of
Done, and often a parent umbrella. The goal is a checklist where every item is
ticked, linked to a `[BUG]`, or marked "intentionally different", plus a
summary comment.

**Do not fix code in QA mode.** A failing item becomes a bug issue, not a
patch. If the owner asks for the fix, pick up that bug as a normal build issue.

### Q1. Accept

Same as step 1, with these differences:
- "Understood" means every checklist item says what to do and what to expect.
- Open PO questions that block an item -> **Needs clarification** and a
  comment, as in step 1.5. Questions that block only some items do not stop the
  rest: accept, run what you can, and leave the blocked items unticked with a
  note.
- Then the Start gate, step 2 (Ready and assign), and set
  **Status = In progress**.

### Q2. Look for existing evidence first

Do not test twice what is already proven. Before running items:

1. Read the parent, the sibling issues, and issues linked from the body or
   comments. Also search the same repo for the feature's name
   (`gh search issues --repo <repo> "<feature>"`).
2. For each checklist item, note whether another issue already tested the same
   scenario, with a date and result (for example a `[TEST]` issue with
   "PASS on <date>"). Also note open `[BUG]` issues that already describe a
   failing item.
3. Reuse it only when the scenario is really the same and the result is recent
   enough to still hold (check the build or release it ran on against now).
   Then tick the item with a link: "covered by #N, PASS on <date>". If the
   evidence is partial, different, or stale, run the item yourself.
4. Never delete or shorten items from the issue's checklist. Link, do not trim.

### Q3. Run the checklist

- Use real data or a real tenant. **Never fabricate test data.** Before
  anything that touches a live customer tenant, even a read-only check, name
  the tenant and get the owner's go-ahead (project rule: confirm the tenant
  first). Without it, the item is **for owner**. Use the `run`
  skill and the repo's own tooling (`skw` in core). Check feature flags and
  permissions first; a missing screen may be configuration.
- One item at a time: do X, observe Y, compare with the expectation. Keep short
  evidence (command and output, query and result, screenshot path).
- Update the checklist in the issue body as you go (`gh issue edit`), not only in
  comments. Keep the rest of the body unchanged.
- Items that need eyes or judgement (layout, wording) or a setup that cannot
  run here -> label **for owner**, unticked, and say why.
- Performance items: run them only with the threshold stated in the issue.
  Load or performance tests against a real tenant always need the tenant named
  and the owner's go-ahead, even when they change no data. If
  none is given, ask for it or leave the item open. Do not invent thresholds.

### Q4. Failures become bugs

**Exception: a `[TEST]` sub-issue from `fix-bug-issue`** (its body links the
fix PR, and its parent is In test). A failing item there is not a new bug:
comment on the `[TEST]` issue and on the PR with what you saw, set the
**parent** back to **In progress**, and stop. The fix goes into the same PR
(run `fix-bug-issue` on the parent; it ignores `[TEST]` sub-issues when
expanding, so its resume check picks up the existing branch and PR).
When every item **passes**, comment "Manual tests passed" on the PR, close
the `[TEST]` issue, and tell the parent's owner it is ready to merge (mention
them on the parent). Don't merge yourself.

For every other failing item:
1. Check for an existing bug first (Q2). If there is one, link it from the item.
2. Otherwise file a `[BUG]` issue with the `create-github-issue` skill: what
   you did, what you expected, what happened, and the evidence. Put it on the
   board and link the QA issue.
3. Mark the item "fails, see #N". The Definition of Done accepts a linked bug.
4. If the item is an expected-but-different behaviour, ask the owner whether it
   is a bug or "intentionally different" before writing either.

### Q5. Tests to add

If the issue lists "automated tests to add", do not write them here. Ask the
owner: file a follow-up build issue (default; title it "Add automated tests
for ...", not `[TEST]`, which would route it into QA mode), or pick them up as
a build issue right now. The Definition of Done accepts a linked follow-up.

### Q6. Summary and status

1. Post one summary comment: passed, failed (with bug links), covered by other
   issues (with links), for owner, and open PO questions.
2. Set **Status**:
   - **In test** when every agent-checkable item is done and only "for owner"
     items remain.
   - **In progress** while items are still open or blocked.
3. When every Definition of Done line is satisfied, ask: "Can I close this?"
   Do not close without a yes.

## Report

Finish with a short summary: issue, final Status, parent Status if it changed,
PR link (build mode), checklist result (passed / failed / covered elsewhere /
for owner), bugs filed, and any open questions. Skipped issues get one line
each with what the owner needs to do.
